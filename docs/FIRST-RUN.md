# First run

The first run should feel like the existing agent environment became coherent around the project, not like another template arrived.

## Invoke

```text
$system-integrate Integrate this project. Inspect the existing system instructions, installed skills, available tools, repository, and current context. Compile the thin system layer first, preserve stronger local rules, rationalize the capability set, then initialize or refresh PROJECT.md and only the supporting context this project needs. Do not stop at an audit.
```

## What the integrator inspects

```text
MODEL ENVIRONMENT
global and project instructions
installed global and project skills
runtime tools and connected sources
on-disk tool configuration surfaces

PROJECT
repository behavior
product surfaces
git history
tests and documentation
existing SYSTEM.md, .system/*, PROJECT.md, and .project/*
first-party evidence available to the host
```

It starts with names, descriptions, scope, and precedence. It reads full instruction and skill bodies only when they are relevant, overlapping, stale, or candidates for change.

## What it builds

The minimum moving-project result is:

```text
SYSTEM.md
PROJECT.md
.project/NOW.md
```

It may also create:

```text
.system/PRODUCT-COHERENCE.md
.system/GTM-ENGINEERING.md
.project/MARKET.md
.project/CAPABILITIES.md
.agents/skills/account-intelligence/
```

Those are examples, not a target set. Several additions may surround one important concern. Conventional functions with no persistent need get nothing, a rare mercy.

## System first

Every system file has a title and one to ten steering lines.

`SYSTEM.md` contains the few beliefs and tensions relevant across consequential work.

`.system/*` contains optional thin lenses for recurring judgment that should load only when relevant. The root file links to every active lens.

System context contains taste and judgment. It does not contain current tasks, project facts, implementation rules, or skill inventories.

## Capability pass

The integrator classifies relevant capabilities as:

```text
keep
route
combine
rewrite
retire
build
expose
leave missing
```

It judges the base model, instructions, skills, tools, scripts, and project context together.

A repeated missing judgment may earn a skill.

Missing live data may require a connector.

Deterministic repeated work may require a script.

A one-time task should simply be completed without founding an internal platform.

Shared global changes remain proposals unless the user explicitly granted authority.

## Project second

After system and capability judgment, the integrator compiles current project truth:

- the simplest accurate product or project sentence
- desired outcome
- why now
- actors and core loop
- responsibility and authority boundary
- entry wedge and destination trajectory
- negative identity
- momentum, bets, contradictions, and next evidence

The system layer shapes judgment. The project layer records reality. They should not repeat one another.

## Expected report

A useful first-run report looks structurally like this:

```text
SYSTEM
Created SYSTEM.md and three routed lenses.

PROJECT TRUTH
Relay completes vendor security reviews and returns defensible proof.

CONTEXT
Rewrote two stale product documents into PROJECT.md, .project/NOW.md,
and .project/PRODUCT.md.

CAPABILITIES
Kept product-design and deep-research.
Routed design-engineering for implementation only.
Combined two byte-identical local research skills.
Built account-intelligence because repeated trigger sensing and account-specific
proof were not covered by the model, current skills, or tools.
Withheld proposed edits to three global skills pending authority.

COHERENCE
Homepage sells an operator; onboarding still teaches a toolkit.

FRONTIER UNLOCK
Current browser reliability may let the product own evidence collection rather
than asking the customer to navigate the workflow.

NEXT PROOF
Run five live reviews and measure unsupported claims, intervention time,
approval cycle, and authority failures.
```

The report is not the product. The changed environment is.

## Review

Reject an integration that:

- produces generic system slogans
- creates one file or skill per department
- lists tools without improving routing
- duplicates project facts into system context
- silently destroys shared global work
- makes the user-facing product harder to explain
- invents evidence to support an exciting trajectory

Accept an integration when the system is thinner, the project is clearer, existing capability is easier to use, and the next ambitious move is grounded in reality.
