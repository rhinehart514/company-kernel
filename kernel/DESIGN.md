# Design

The interface is the product's explanation of itself.

AI can generate more surfaces, states, content, and interaction paths than a team could design by hand. That does not give users more attention, better memory, or greater willingness to learn the machinery.

Intelligence behind the interface should reduce what the user has to understand.

It should not create another cockpit for supervising the intelligence.

## Design the mental model before the screen

Decide what the user believes the product is, what objects exist, what can happen to them, what state matters, and where responsibility sits.

Then design the interface.

A polished surface cannot rescue a broken product model. Visual hierarchy becomes decoration when the underlying concepts compete.

Keep the number of durable concepts small. Let capability expand beneath them.

The user should feel the product becoming more powerful, not spreading sideways.

## Make the next move obvious

At every consequential state, the interface should answer:

- where am I
- what is true now
- what can happen next
- what the system is doing
- what requires my judgment
- what completed
- what failed
- how I recover

Do not make users reverse-engineer workflow state from disabled buttons, notification noise, or a dashboard assembled around available data.

Hierarchy is a decision about attention.

Spend it on the action, evidence, exception, or choice that matters now.

## Let intelligence remove interface

A capability does not automatically deserve a page, mode, panel, agent, or settings screen.

Use good defaults when the system has earned confidence.

Infer when inference is safe and reversible.

Ask when preference, consent, ambiguity, consequence, or authority makes human judgment essential.

Generate a temporary surface when the need is contextual. Create a durable surface when users need continuity, navigation, memory, comparison, or control.

The best interface for a capability may be behavior that simply happens correctly.

## Keep generated experiences coherent

Dynamic interfaces may adapt to intent, role, state, evidence, and task.

Adaptation should preserve orientation.

Stable objects, language, placement, state, and action meaning give users enough continuity to trust a changing surface.

Do not personalize the product into a different mental model for every session.

Generated does not mean arbitrary.

## Design authority, not just actions

When the product can act, show what it may do, what it did, what it will not do, and where control returns to the user.

Make consequential delegation explicit.

Distinguish suggestion, draft, approval, execution, completion, exception, and reversal.

Do not use a friendly interface to hide an unsafe responsibility boundary.

Trust comes from legible capability, bounded authority, credible proof, and recoverable failure.

## Build proof into the experience

Show evidence at the moment the user needs confidence.

Provenance, completion state, timestamps, changes, assumptions, sources, approvals, and exceptions matter only when they help the user decide whether to trust the result or act next.

Do not turn proof into a forensic archive the user must excavate.

Dense proof beats abundant telemetry.

## Design every state that can become real

The product includes:

- first use
- empty states
- loading and long-running work
- partial completion
- degraded capability
- permission boundaries
- conflicting inputs
- exceptions
- failure
- recovery
- irreversible action
- return after time away

A happy-path mockup is not the experience. It is the least informative slice of it.

Make exceptional states feel like part of the same product rather than evidence that the interface ended where engineering became inconvenient.

## Use familiar patterns as leverage, not destiny

Familiar interaction lowers learning cost.

Use it where novelty does not buy a better product model.

Break convention when a new capability, responsibility, or workflow needs a genuinely better form. Then make the new form teach itself through structure and behavior rather than explanation.

Do not ship the market's current layout merely because component libraries made it cheap.

A product should have a point of view visible in what it removes, emphasizes, sequences, and refuses.

## Design the whole product surface

The product may appear through UI, agent behavior, APIs, integrations, messages, generated artifacts, humans, and support.

Make them speak one language and preserve one state model.

Do not expose internal teams, services, agents, or handoffs as separate products unless the user benefits from the distinction.

## Do not inherit

Do not assume:

- more capability requires more interface
- dashboards create clarity
- configuration creates control
- generated interfaces may change without stable anchors
- visual polish can compensate for conceptual debt
- every user should see every capability
- familiarity is always better than a new interaction
- design begins after the product decision
- empty, error, and recovery states are edge work
- an AI product should look like a chat box

## Human gate

Escalate changes to the core product model, consequential authority, irreversible action, trust model, accessibility boundary, public identity, or experience promise.

The agent may simplify hierarchy, collapse redundant surfaces, improve states, strengthen defaults, and test reversible interaction variants when the product truth is clear.

## Done

Design is done when the user can understand what the product is, see what matters now, delegate with appropriate confidence, recover when reality diverges, and gain more capability without carrying the system's complexity in their head.
