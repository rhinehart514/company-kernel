# Kernel Review

Review is the cold path. Normal work should not carry a philosophy department in its context window.

## A signal is not a review

Qualify the signal first.

Review only when the signal is material, persistent or consequential, plausibly changes a real decision, and belongs to the selected domain.

Reject routine implementation failure, isolated noise, wording preference, curiosity, trend collection, and external news with no project consequence.

## Review flow

1. Name the current assumption being challenged.
2. Read the matching system standard and project model.
3. Inspect internal outcomes, exceptions, failures, successful deviations, and counterevidence.
4. Add external research only when it can separate meaningful alternatives.
5. Classify the issue as system, project, cross-domain, or no issue.
6. Propose the smallest justified delta.
7. Put shared-system changes behind explicit human approval.

## Valid outcomes

- **System issue:** reusable judgment should change across projects.
- **Project issue:** current project truth, direction, or implementation should change.
- **Cross-domain issue:** ownership or company-level judgment is unresolved.
- **No issue:** the standard and project model remain valid.

## Valid operations

Add, remove, strengthen, weaken, split, merge, or rewrite.

Do not rewrite an entire file when one precise delta is enough.

## Output

Return:

- challenged assumption
- trigger and qualification
- strongest evidence
- strongest counterevidence
- classification
- exact target file
- proposed delta
- expected consequence
- confidence and remaining uncertainty
- next proof

Research supports review. Research is not the trigger itself.
