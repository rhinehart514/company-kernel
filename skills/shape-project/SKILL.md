# Shape Project

Turn a cold repository and founder conversation into enough shared judgment
for a capable agent to move hard without constant re-briefing.

Use `$venture-judgment` first. Load worldview, writing, and only the domain
references that can change this project.

This skill adapts Matt Pocock's design-tree and frontier grilling method under
MIT. See `THIRD_PARTY_NOTICES.md`.

## Modes

- **shape:** establish a new or poorly understood project
- **refresh:** rewrite context after material evidence or direction changes
- **rescue:** recover a project whose code, product, and stated direction disagree

## Inspect before asking

Read what the environment can show:

- repository structure and behavior
- existing instructions and context
- current product surfaces
- recent commits and active work
- tests, runtime evidence, and deployments
- available tools and skills
- first-party customer, market, or company material available to the session

Research factual unknowns when they can change a decision.

Do not ask the founder to inventory what you can inspect.

Code proves capability. It does not prove the complete company model.

## Build the design tree

Map the decisions that define the project. Each decision branches into the
decisions that depend on it.

Work in rounds.

The **frontier** is every consequential decision whose prerequisites are
settled enough to ask now.

Ask the whole frontier in one round, usually three to seven questions.

For every question:

1. name the decision clearly
2. explain why it matters
3. show materially different options when useful
4. give your recommended answer
5. push beyond the founder's starting frame when a larger coherent option exists

Facts are the agent's job.

Decisions are the founder's.

Do not ask a downstream question while its prerequisite remains unresolved.

Recompute the frontier after every round.

## Ideate while resolving

Do not merely extract what the founder already thinks.

Use current capabilities and the shared worldview to ask:

- which boundary exists only because software used to be expensive?
- what could this product responsibly own now?
- are we choosing a wedge or accidentally choosing a small company?
- what would make the old workflow feel obsolete?
- what can multiply without multiplying the user's mental model?
- which cheap bets should compete before evidence forces concentration?
- what experience tokens can compound into advantage?
- what product plus GTM move creates a faster path to reality?

Recommend the strongest call. Do not hide behind a menu.

## Resolve the project

The design tree should settle enough to state:

- identity
- primary actor
- outcome
- why now
- company thesis
- product model
- responsibility boundary
- core loop
- market entry and wedge
- compounding direction
- important decisions and constraints
- strongest evidence
- unknowns that can change direction
- continuation and kill conditions
- non-goals
- next proof

When the frontier is empty, summarize the model and get one confirmation that
shared understanding has been reached.

Then write.

## Write only three files

Create or update:

```text
AGENTS.md
PROJECT.md
NOW.md
```

Preserve existing `AGENTS.md` rules. Add or replace only a marked Company
Kernel route.

`PROJECT.md` is durable founder judgment, not an intake form.

`NOW.md` is the current edge, not a backlog or transcript.

Use the output contract below.

### AGENTS.md route

```md
<!-- company-kernel:start -->
Read `PROJECT.md` before consequential work.
Read `NOW.md` when current direction, active bets, recent evidence, or the
next proof matters.
Use installed Company Kernel skills for consequential company and product
judgment.
Update durable context only when evidence materially changes it.
<!-- company-kernel:end -->
```

### PROJECT.md contract

Write the smallest coherent document that lets a fresh agent explain:

- what the project is
- what must become true
- who it is for
- why now
- what the product owns and refuses
- how value is created and proved
- how the first wedge can become a larger company
- what decisions are already made
- what evidence should change the model

Use exact project language. Omit sections that add no decision value.

### NOW.md contract

Keep only:

- current outcome
- active bets
- recent evidence
- open decision-changing unknowns
- immediate constraints
- next proof

## Refresh without sediment

On refresh, inspect reality again.

Rewrite invalidated truth.

Delete dead context.

Move temporary state to `NOW.md`.

Do not append a second contradictory project model.

Do not preserve the interview transcript.

The finished context should be smaller than the confusion it replaces.
