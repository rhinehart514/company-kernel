# Product

Product decides what should exist, what outcome it should own, and what should
disappear again.

## Build more. Make users understand less.

AI makes capability production cheap.

It does not make the user's mental model cheap.

A product can contain many capabilities and still feel like one thing.

A product with three disconnected ideas can already be too large.

Add capability aggressively. Add concepts reluctantly.

Before creating another page, mode, agent, workflow, or product, ask whether
the capability can become:

- invisible behavior
- a strong default
- an action on an existing object
- a state in an existing loop
- an extension of an existing surface
- a replacement for an old workflow
- an integration
- nothing

The best addition often makes the product more powerful without making the
product feel bigger.

## Start from the outcome

Define what becomes true for the user, operator, customer, or business.

Features, interfaces, agents, workflows, services, and humans are
implementation choices beneath that result.

Do not inherit the market's current product boundary automatically. It may
exist because software could not previously understand, decide, coordinate,
generate, or act.

Ask how much more of the outcome the product can responsibly own now.

## Responsibility has a surface

Moving from assist to complete to operate is not a copy change.

Larger responsibility requires:

- capability
- authority
- evidence
- reliable state
- exception handling
- recovery
- understandable user control
- economics that survive the service level
- a clear cutoff where responsibility returns to a person or customer

Do not claim ownership the system cannot defend.

Do not stop at assistance merely because the market is used to doing the rest
manually.

## Minimum means minimum distance to evidence

MVP was useful when implementation was a major cost of learning.

Do not turn the old cost constraint into an aesthetic.

Build the smallest credible test of the important uncertainty.

If trust, integration, repeated use, real completion, or willingness to pay is
the uncertainty, a toy prototype is not an MVP. It is avoidance with a URL.

If several credible variants are cheap, comparison may teach more than early
commitment.

## Use multiple wedges without inventing multiple companies

Several audiences, entries, utilities, demos, or surfaces can be coherent when
they resolve to:

- one underlying promise
- one capability system
- one product model
- one compounding trajectory

The customer does not need to see the organizational explanation.

If every wedge requires a new mental model, new architecture, new brand, new
delivery system, and unrelated proof, the company is probably fragmenting.

## Spend experience tokens

Observe what users attempted, expected, misunderstood, worked around,
delegated, abandoned, and paid for.

Turn:

- repeated exceptions into explicit states
- repeated workarounds into capabilities
- repeated configuration into defaults
- repeated supervision into safer autonomy
- repeated explanation into product behavior
- repeated failure into removal

The product should become more opinionated as the company earns the right to
have opinions.

## Kill conceptual debt

Features create code debt.

Concepts create experience debt.

Code can increasingly be rewritten cheaply. A confused product model is harder
to repair.

If two concepts do the same job, collapse them.

If a setting can become a reliable default, remove the setting.

If a workflow can disappear, do not improve the workflow.

If a new surface exists because implementation was convenient, reconsider the
boundary.

Remove before organizing.
