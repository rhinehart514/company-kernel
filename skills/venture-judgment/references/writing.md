# Writing durable context

The model experiences tokens, not the architecture diagram.

Writing is part of the system.

## Assume intelligence. Never assume context.

Do not explain common knowledge to a frontier model.

Do explain:

- what world the conclusion comes from
- which old assumption changed
- what remains scarce
- the distinction that resolves the tradeoff
- what behavior changes because of it
- what evidence should override it

A compressed conclusion without its roots becomes a fortune cookie.

## Transfer judgment, then ambition

Bad context transfers rules.

Good context transfers judgment.

Exceptional context gives the model a better object to think with.

Useful concepts compress a real decision surface:

- experience tokens
- conceptual cost
- responsibility surface
- evidence velocity
- earned complexity
- proof density
- terminal, exception, and cutoff states

Do not coin language for decoration. A concept earns its name when it makes
new reasoning easier.

## Write with pressure

Weak:

> Consider maintaining product coherence as new features are added.

Stronger:

> Add capability aggressively. Add concepts reluctantly.

Then give the line roots:

> Code became cheap. User comprehension did not. Before creating a surface,
> ask whether the capability can become a default, action, state, extension,
> or replacement inside the product users already understand.

The first line creates pressure.

The second paragraph transfers the model behind it.

## Prefer concrete contrast

Use exact nouns and visible consequences.

Weak:

> Avoid unnecessary complexity.

Stronger:

> A new abstraction must remove more complexity than it introduces.

Weak:

> Focus on outcomes.

Stronger:

> Start from what must become true. Features, agents, workflows, and
> interfaces are implementation choices beneath that result.

Contrast defines the decision boundary better than a polite principle.

## Make the prose think further

A durable section should leave the model able to derive decisions that were
not enumerated.

Ask of every section:

- does this change a likely decision?
- does it reveal a non-obvious distinction?
- does it expand the size of the possible outcome?
- does it explain when the call stops being true?
- could a capable model have generated this without company context?

If the file merely says to build good products, write clean code, research
carefully, and listen to users, delete it.

## Keep the voice alive

Write plainly.

Use short sections.

Lead with the call.

Use verbs.

Let strong sentences stand.

Avoid corporate filler, framework theater, fake neutrality, excessive
qualification, and headings that merely rename the paragraph.

The prose should feel like a very good founder is sitting beside the agent,
not like the Department of Product Development discovered Markdown.

Be ambitious as fuck.

Do not become vague.
