# Product Coherence

Make the product more powerful without making it feel larger.

Use `$venture-judgment`. Load product, design, software, customer, worldview,
and writing. Add strategy or GTM when the change affects the wedge, promise,
or company trajectory.

Read `PROJECT.md`, `NOW.md`, the actual product surfaces, flows, terminology,
state model, and implementation before making the call.

## Modes

- **before:** decide what form a proposed capability should take
- **after:** inspect what was built and remove product entropy
- **audit:** map the current product model and identify the highest-leverage collapse

## Map the product first

State:

- primary actor
- promised outcome
- product model
- core loop
- responsibility boundary
- concepts the user must understand
- durable surfaces
- important states
- proof and recovery
- current wedge
- capabilities hidden behind the experience

Do not judge coherence from screenshots alone.

A visually consistent product can still contain several contradictory mental
models.

## Classify the change

Make one primary call:

- absorb into an existing concept
- make it invisible behavior
- make it a default
- make it an action
- make it a state
- extend an existing surface
- replace an existing concept or workflow
- create a new surface
- separate it deliberately
- kill it

A new surface is not the neutral option.

It carries conceptual cost forever.

## Run the coherence tests

Ask:

- does this increase capability or merely increase product area?
- can the user explain it using concepts they already know?
- does it strengthen the core loop?
- what old workflow, setting, page, or explanation becomes unnecessary?
- are we exposing implementation machinery because it was easy to build?
- does the change create a second product model?
- can multiple wedges still resolve to one promise and capability system?
- does the company now claim more responsibility?
- can capability, authority, proof, exceptions, and recovery defend that claim?
- does the interface reveal state and control without making the user operate the agent?
- will the change make the product easier or harder to describe and sell?

A feature can be cheap and still make the product expensive to understand.

## Make the call

Lead with the product decision.

Then state:

- why
- conceptual cost
- responsibility change
- affected surfaces
- what should be removed or absorbed
- implementation consequence
- proof required
- failure and recovery consequence
- what evidence would reopen the call

Do not produce a neutral audit that leaves the hard choice to the reader.

## Repair the implementation

When the task grants authority, make bounded changes that restore coherence:

- collapse duplicated concepts
- remove redundant navigation
- replace configuration with earned defaults
- unify language
- move capability into the core loop
- delete old paths made obsolete
- expose necessary proof, state, or recovery
- hide internal agent machinery
- align the code boundary with the product boundary

Do not use product coherence as permission for an unrelated redesign.

## Preserve durable truth

Update `PROJECT.md` only when the product model, outcome, wedge,
responsibility boundary, or important decision materially changed.

Update `NOW.md` when the current bet or next proof changed.

Do not create another domain file.

The finished product should feel like it learned how to do more, not like
another product moved in.
