# Product coherence

The company can be enormous. The user's mental model should remain small.

A clear product truth answers:

- what this is
- who or what it is for
- what work or outcome it owns
- what the user provides
- what happens next
- what proves completion

The current entry and the larger destination are different truths.

The entry explains adoption now.

The trajectory explains what winning this entry makes credible next.

Do not average them into vague platform language.

The core loop matters more than the feature inventory:

```text
intent
→ system action
→ result
→ proof
→ next value
```

A new capability belongs when it makes the central promise more complete, more powerful, easier to trust, or easier to reach.

A merely useful capability may still be another product.

Increasing capability should not automatically increase navigation, configuration, modules, dashboards, or concepts exposed to the user.

Product, positioning, sales, onboarding, delivery, support, and proof should describe the same responsibility.

Negative identity protects coherence:

```text
what this is not
what work the user should never need to understand
what surface should remain hidden
what adjacent opportunity would turn this into another company
```

When cheap implementation removes the cost governor, product taste becomes the governor.
