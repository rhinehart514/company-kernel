# Capability judgment

A capability is the combination of model intelligence, durable steering, access, tools, deterministic machinery, and project truth required to perform a repeated job well.

Do not equate a folder of skills with capability.

## Resolve gaps in this order

```text
base model
  -> can it already do the job well with current project context?
existing skill
  -> does a routed installed skill add the missing judgment or workflow?
available tool or source
  -> is the real problem access to current data or external action?
deterministic code
  -> is a bounded repeatable operation better expressed as a script or test?
new skill
  -> does a repeated non-obvious job still remain?
```

Sometimes the correct result is to leave the gap visible because the current environment cannot supply it reliably.

## Capability actions

- **keep:** useful, current, and correctly scoped
- **route:** strong capability exists but activation or ownership is unclear
- **merge:** trigger, judgment, authority, resources, and result genuinely duplicate
- **rewrite:** useful capability is bloated, stale, host-bound, or compensates for an old model weakness
- **disable or retire:** persistent steering no longer improves behavior
- **build:** a repeated job deserves a project-local skill, script, adapter, context surface, or tool
- **expose:** a useful tool or evidence source exists but is not reachable or legible

Prefer routing over merging when distinctions are uncertain. Do not silently mutate user-level capabilities.

## Multiple capabilities are allowed

Do not create one skill per department and do not force one skill to own an entire department.

Several capabilities may sit near the same area when their triggers, evidence, authority, or artifacts differ. Account discovery, trigger sensing, demo generation, procurement navigation, and pipeline analysis may all be distinct without requiring a generic `gtm` skill.

Likewise, one capability may cross product, research, design, engineering, and GTM because the repeated outcome crosses those labels.

## Diagnose the actual gap

```text
missing judgment       -> thin steering or skill
missing workflow       -> skill, perhaps with scripts
missing access         -> connector, tool, permission, or explicit limitation
missing computation    -> script, code, test, or service
missing project truth  -> project context or research
missing reliability    -> verification, recovery, observability, or narrower authority
missing model ability  -> do not conceal it with ceremonial prompting
```

Build project-local first. Promote to user scope only after the capability proves useful across unrelated projects.
