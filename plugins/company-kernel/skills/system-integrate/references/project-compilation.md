# Project compilation

After the thin system layer is established, compile the smallest current model of the project that lets a capable agent decide and act well.

## Core set

A moving integrated project normally begins with:

```text
SYSTEM.md
PROJECT.md
.project/NOW.md
```

Optional `.system/*.md` files hold thin durable judgment for selected work.

`PROJECT.md` holds compressed current project truth and routes to supporting context.

`.project/NOW.md` holds the fast-changing objective, momentum, bets, constraints, contradictions, and next evidence.

## Product and project truth

The root project truth should make clear:

- what this is now
- what must become true
- why now
- who or what participates
- how value is created and proven
- what responsibility the project owns
- why someone enters now
- what winning the entry unlocks
- what the project refuses to become
- where current supporting context lives

For a user-facing product, the largest company can still have the smallest product sentence.

Capability may expand while visible complexity contracts. A useful feature can still be the wrong product.

## Adaptive files

Split only across a real boundary of cadence, authority, audience, ownership, risk, or size.

Several files may cover one complex concern:

```text
.project/PRODUCT.md
.project/PRODUCT-SURFACES.md
.project/USER-LOOP.md
.project/MARKET.md
.project/ACCOUNT-SIGNALS.md
.project/SALES-MOTION.md
.project/DISTRIBUTION.md
.project/DELIVERY.md
.project/AGENT-AUTHORITY.md
.project/ECONOMICS.md
.project/EVIDENCE.md
.project/CAPABILITIES.md
```

These are examples, not a checklist. Do not reward symmetry.

## Ambition and coherence

Keep two truths distinct:

```text
entry truth        why the project wins attention or adoption now
trajectory truth   what winning the current loop makes credible next
```

The trajectory should be an unlock chain through data, authority, trust, distribution, capability, economics, or system position, not a paragraph about becoming a platform.

GTM, product behavior, onboarding, delivery, and proof should make the same promise.

System context can preserve product taste. Project context must still describe what is actually true.

## Evidence

Distinguish authorized direction, observation, inference, active bet, contradiction, and unknown.

Use dates or provenance for dynamic claims when staleness matters.

Code proves capability, not demand. Requests do not automatically become strategy. Generated synthesis is inference.

Rewrite stale truth. Git preserves history; current context should not preserve every previous company simultaneously.

## Non-startup projects

Pursue the largest coherent consequence supported by the project's purpose.

For open source, research, civic, internal, or creative projects, adapt the model around adoption, ecosystem leverage, knowledge, public value, operating improvement, or another real outcome instead of forcing buyers, pipeline, and venture language.
