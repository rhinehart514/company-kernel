# Kernel review

Question the current judgment only when reality earns the interruption.

## Modes

- **qualify:** decide whether a signal deserves review
- **review:** inspect evidence and propose a delta
- **audit:** compare standards and project models without changing either

## Select the domain

Choose Coding, Product, GTM, or an explicit cross-domain review.

Read [the protocol](references/PROTOCOL.md) and only the matching domain review file. Then read the current system standard, project model, and relevant evidence.

Do not load every domain because the company possesses several nouns.

## Qualify the signal

A review requires a material, persistent or consequential signal that can plausibly change a real decision and belongs to the selected domain.

Reject routine implementation failure, isolated noise, wording preferences, curiosity, and trends with no project consequence.

## Gather evidence

Use internal outcomes first. Add repository analysis, customer or buyer evidence, connected sources, web research, current primary sources, experiments, or direct market contact only when they can separate meaningful alternatives.

Research supports review. Research is not the trigger itself.

Look for counterevidence. Stop when more evidence is unlikely to change the classification or next test.

## Classify

Every finding must be one of:

- **system issue:** transferable judgment should change
- **project issue:** current project truth or direction should change
- **cross-domain issue:** ownership or company-level judgment is unresolved
- **no issue:** current standards and models remain valid

## Propose the smallest delta

Name the challenged assumption, strongest evidence and counterevidence, exact target file, operation, expected consequence, confidence, and remaining uncertainty.

Operations are: add, remove, strengthen, weaken, split, merge, or rewrite.

Do not rewrite whole files when a precise delta is enough.

## Authority

Agents may qualify, research, compare, challenge, and propose. Shared system standards change only after explicit human approval.

When authorized, project-model changes may be applied. Otherwise return the proposed patch and next proof.
